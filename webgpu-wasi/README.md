# webgpu-wasi

`webgpu.h` (the standard C header from
[webgpu-native/webgpu-headers](https://github.com/webgpu-native/webgpu-headers))
implemented over `wasi:webgpu@0.0.1`, for C and C++ guests built with wasi-sdk
for wasm32-wasip2. A module links it and calls `wgpu*` as it would against
wgpu-native or Dawn; the component that comes out imports
`wasi:webgpu/webgpu@0.0.1`, which the ffrwd sidecar hosts for a module
granted `-gpu`.

It lives in this package for now and depends on nothing in it: the directory
can be moved to a repository of its own as is.

## Layout

* `include/webgpu/webgpu.h`: the header, webgpu-headers at 91beced (BSD-3-Clause,
  `include/webgpu/LICENSE`).
* `wit/`: the world the shim is written against (`world.wit`) and the WIT it
  pulls in under `deps/`: `wasi:webgpu@0.0.1` and `wasi:graphics-context@0.0.1`
  from the wasi-gfx proposal's v0.0.1 branch, and `wasi:io@0.2.0`
  (Apache-2.0 WITH LLVM-exception, `wit/LICENSE`).
* `generated/`: wit-bindgen's C bindings for that world, checked in.
* `src/webgpu_wasi.c`: the implementation. `src/enums.h` converts enums between
  the two sides and is generated by `tools/gen_enums.py`.
* `CMakeLists.txt`: the `webgpu` target, the name PyroWave's WebGPU CMake (and
  most `webgpu.h` projects) look for.

Regenerating, from this directory, with wit-bindgen-cli 0.62 or newer:

```
wit-bindgen c wit --world webgpu-wasi --rename wasi:io/poll@0.2.0=webgpu_wasi_poll --out-dir generated
python tools/gen_enums.py
```

`wasi:io/poll` is renamed so that a module whose own bindings also import
`wasi:io` does not get two definitions of the same C names.

## Coverage

The compute side of `webgpu.h`:

* Instance: `wgpuCreateInstance`, `wgpuInstanceRequestAdapter`,
  `wgpuInstanceProcessEvents`, `wgpuInstanceWaitAny`,
  `wgpuInstanceHasWGSLLanguageFeature`, `wgpuHasInstanceFeature`,
  `wgpuGetInstanceFeatures`, `wgpuGetInstanceLimits`.
* Adapter: info, limits, features, `wgpuAdapterRequestDevice`.
* Device: limits, features, adapter info, queue, error scopes, destroy, and
  the create functions for buffers, textures, samplers, shader modules (WGSL),
  bind group layouts, bind groups, pipeline layouts, compute pipelines,
  command encoders and query sets.
* Buffers: map (read and write), mapped at creation, `GetMappedRange`,
  `GetConstMappedRange`, `ReadMappedRange`, `WriteMappedRange`, unmap,
  destroy, size, usage and map state.
* Textures and views, command encoding (compute passes, buffer and texture
  copies, clear, query resolve), compute passes (pipeline, bind group,
  dispatch, indirect dispatch), queue submit, `WriteBuffer`, `WriteTexture`,
  `OnSubmittedWorkDone`.
* `AddRef` and `Release` for all of the above.

Not here: render passes and pipelines, render bundles, surfaces, the async
pipeline creation calls and compilation info. A module that calls one of those
fails to link, rather than at run time.

## How waiting works

`wasi:webgpu@0.0.1` is the WASI 0.2 version of the interface. The operations a
browser runs asynchronously (`request-adapter`, `request-device`, `map-async`,
`pop-error-scope`, `on-submitted-work-done`) are blocking calls there: they
return once the host has the answer. So by the time a `webgpu.h` function that
returns a `WGPUFuture` returns, the operation has completed, and what the
callback mode still decides is when the callback runs:

* `WGPUCallbackMode_AllowSpontaneous`: at once, inside the call.
* `WGPUCallbackMode_AllowProcessEvents`: in the next `wgpuInstanceProcessEvents`,
  or in a `wgpuInstanceWaitAny` naming the future.
* `WGPUCallbackMode_WaitAnyOnly`: in a `wgpuInstanceWaitAny` naming the future.

`wgpuInstanceProcessEvents` never blocks, and `wgpuInstanceWaitAny` has
nothing to wait for, so the `TimedWaitAny` instance feature is offered and
any timeout is met. The one WASI pollable 0.0.1 has, a device's
`onuncapturederror-subscribe`, is checked without blocking in both, and each
time it is ready the device's uncaptured error callback runs. The interface
cannot say what the error was, only that there was one; the ffrwd host prints
it to stderr.

`wasi:webgpu` 0.3 (WASI 0.3) makes those operations async functions, which is
where waiting on real pollables belongs; the upstream shim for it is
[wasi-webgpu-headers](https://github.com/wasi-gfx/wasi-webgpu-headers).

## How mapping works

A mapped range is a copy in linear memory. Mapping for reading copies the
range out of the host (`get-mapped-range-get-with-copy`) the first time the
guest asks for a pointer into it; mapping for writing, and mapping at
creation, gives the guest a zeroed buffer that `wgpuBufferUnmap` writes back
(`get-mapped-range-set-with-copy`). Pointers returned by `GetMappedRange` stay
valid until the unmap.

## Using it

With CMake, `add_subdirectory(webgpu-wasi)` and link `webgpu`. Without it,
compile `src/webgpu_wasi.c` and `generated/webgpu_wasi.c` with `include/`,
`generated/` and `src/` on the include path, and link
`generated/webgpu_wasi_component_type.o` into the component so its imports are
declared. Nothing is thread safe; wasm32-wasip2 has no threads.
